# Why the pilot does not scale

A demonstration succeeds with a chosen question and a clean folder of documents.

Production has changing documents, users with different entitlements, real permissions, outages, and a support queue. The gap between those two is where most AI projects quietly stop, and it is rarely a model problem.

## What actually blocks it

Our assistant might fail to scale because:

- Policy ownership is unclear, so nobody can say which version is authoritative.
- Retired documents still sit in three repositories, and only one of them was cleaned.
- Access rights do not carry correctly into the search index, so the index is more permissive than the source systems.
- Nobody owns the knowledge base, so it ages.
- Two policies conflict and there is no process for resolving that, because previously a human just picked one.

Read that list again. None of them are fixed by a better prompt, a bigger model, or more few-shot examples. They are ownership and data problems wearing an AI costume.

<Callout type="important" title="The uncomfortable version">
  If the underlying process is confused, an assistant does not clarify it. It makes the confusion faster, more fluent, and more convincing — which is worse than the confusion was on its own.
</Callout>

## Map the process before you automate it

Before adding anything, answer these about the existing workflow:

- Who writes a policy?
- Who approves it?
- How does an employee know the version they are reading is current?
- What happens today when two policies conflict?
- Who retires the old one, and how long does that take?

If these have no answers, that is your project. The assistant comes after.

There is an old principle here that predates all of this: automating a broken process gives you a faster broken process. It is more true now, not less, because the automation is persuasive.

## Choose a proportionate solution

Worth asking honestly, because the answer is sometimes no.

| The need | What might be enough |
| --- | --- |
| Find the right policy document | A well-indexed search over well-maintained documents |
| Apply a fixed rule to a clear input | Rules, or a form with validation |
| Explain across several documents, in context | This is where generative answers genuinely help |
| Take an action once a decision is made | Workflow automation, with the decision still owned |

Generative answers earn their place when users need an explanation drawn across documents. That benefit comes with the evaluation and control work of the previous four lessons, so it should be a choice rather than a default.

## Data movement is a real constraint, and not a blanket rule

You will hear that data "cannot leave the country" or "cannot go to a third party". Sometimes true, often more specific than the sentence suggests.

What actually governs it: your organisation's policy, the contracts you signed, and the law applicable to that data in that context. Those three can point in different directions. Assess the actual position for the actual data rather than adopting either a blanket prohibition or a blanket permission — both are usually wrong and both are stated with equal confidence.

## People, not just systems

Scaling depends on three groups nobody puts in the architecture diagram.

**Users** need to understand the boundary, or they will ask it things it was never approved for and act on what comes back. **Support teams** need diagnostic information — if a user reports a bad answer, somebody has to be able to find out which document produced it. **Owners** need time and authority to maintain the thing, which means it has to appear in someone's objectives rather than being a side project that a keen person runs.

<Callout type="tip" title="Worked example">
  Fix policy version ownership and retirement <em>before</em> expanding the knowledge base. Adding documents to an unmanaged base increases apparent coverage while reducing reliability — the assistant answers more questions and is right less often, which is the worst possible combination.
</Callout>
